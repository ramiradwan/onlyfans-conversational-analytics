# Optional computation worker

This executable implements the private `nlp-child.v1` framed transport and existing `nlp-worker.v2` messages. It is started only by the installed native owner with explicit inherited pipes and an owner-context handle. It has no standalone activation, listener, database or network authority. Default application construction does not configure it.

`boundary_entities` version1 accepts one closed shared-boundary entity graph ABI, CPU execution and authenticated logical data bindings. It advertises only concept mentions. Configuration maps each stable `label_id` and matching `concept_id` to a separate `model_label`; output selection does not change the ordered model conditioning. Labels, descriptions and supported settings belong to the admitted profile/configuration. Missing tasks are unavailable, not empty results. Graph/tokenizer changes require a new admitted component identity.

`boundary_topics` version1 implements `message_topics.v1` with the `onnx-boundary-classification.v1` ABI and `huggingface-tokenizer-json.v1` tokenizer. Its four logical data members are encoder, classifier, tokenizer and `boundary-topic-config.v1` configuration. Only the encoder may retain `onnx-boundary-entity.v1` when sharing that exact artifact with an entity component. Both adapters share the bounded CPU runtime and unload sessions between serial components.

Topic configuration binds ordered labels/descriptions, task instructions, file identities, component policies and explicit decoding settings. [topic.rs](src/topic.rs) defines the fields, supported policies and bounds. All conditioning is retained when returning a subset. Independent sigmoid decisions use the configured temperature and inclusive threshold, support valid empty results, and emit uncalibrated probabilities or absent scores. Empty or whitespace-only source returns no findings before tokenization or inference. Up to 64 labels and findings are supported; there are no default categories or thresholds.

An optional `groups` array in `boundary-topic-config.v1` selects separate classification views. Each group has exactly `group_id`, `task_name`, `instruction` (string or null), and `label_ids`. Group identifiers are unique; each nonempty label list follows the global label order, and the groups together include every global label exactly once. Group task names and instructions determine their prompts; model labels and descriptions come from the existing ordered bindings. Every complete view is admitted before inference. Finite outputs from all views are assembled in global order before any findings are returned; a failed view fails the assessment. Omitting `groups` preserves flat conditioning. Grouped configuration requires an updated worker: older workers reject the additional field, and profiles must bind the exact compatible worker and configuration artifact identities. The graph ABI is unchanged and the encoder/classifier sessions are reused between groups.

Both adapters reject non-null tokenizer JSON `truncation` before initialization. The streaming check validates complete JSON and unique root fields, skips vocabulary values, polls cancellation/deadline, and limits files to 64 MiB, 64 root fields and 256 bytes per root key. Topic processing rejects truncated words or excessive complete encoded input before inference. Coverage and hashes refer to the original message. Profile v2 retains homogeneous weight formats; v3 permits mixed formats with exact per-role compatibility checked during preparation.

Prepare outside the source checkout with `tools/nlp-worker/prepare.py --source <clean pinned upstream checkout> --target <fresh build directory> --product-revision <full commit SHA>`. Both source trees come from Git blobs; product working-tree edits and untracked or ignored files are excluded. Preparation requires regular non-executable source files and validates the required members and upstream patch seams before creating the target. The `nlp-worker-build.v2` receipt records both commits, input blob identities and hashes, the executing preparer hash, and the complete prepared file inventory. Existing version 1 receipts retain their historical meaning.

Then use Cargo with `--locked --offline -j2`. No download feature, model acquisition or runtime environment override is used. The prepared crate retains the upstream Apache2.0 notices. Source preparation does not qualify a compiled worker, model or installed package. Ordinary application builds do not invoke this preparation or enable the provider.

The native owner must retain read-only, identity-checked artifacts and executable/runtime package observations through child drain, enforce the caller's memory/deadline policy and join the exact worker Job. An unload drops the component sessions/tokenizer; closing the process releases its CPU runtime. Cancellation cooperates between stages; an uninterruptible stage remains subject to the owner's bounded termination/join. Neither a handshake nor a preparation response grants release approval or user authorization.

The optional `instruction-topics` Cargo feature adds `instruction_topics` using the llama.cpp b11669 C ABI (commit `620d2225cc436ab0b001e3200e590e3b286ef9ab`). Set `LLAMA_CPP_INCLUDE` at build time to the exact official headers; `build.rs` checks each SHA-256 before compiling the in-process bridge. Preserve upstream MIT notices with the build inputs. No runtime is linked into the base application or acquired by this build.

This adapter declares architecture `llama-b11669-cpu-v1`, weights `gguf-model.v1`, and tokenizer `gguf-embedded.v1`. The tokenizer closure is the single model artifact, whose bytes contain its vocabulary. The four component artifacts are model, system prompt (`instruction-system-utf8.v1`), grammar (`llama-gbnf.v1`), and `instruction-topic-config.v1`. The configuration fields are `schema`, `model`, `system_prompt`, `grammar`, `runtime`, `labels`, `policies`, `context_tokens` (8192), `output_tokens` (192), and `inference_threads` (2 or 8). The `runtime` object maps the exact names `libomp.dll`, `ggml-base.dll`, `ggml.dll`, exactly one of `ggml-cpu-x64.dll` or `ggml-cpu-alderlake.dll`, and `llama.dll` to profile runtime artifact IDs with format `llama-b11669-cpu.dll.v1`. Every runtime file is owner-bound and its complete ordered hash closure is pinned for the process lifetime. Only the bound explicit CPU backend is registered. The four shared VC runtime libraries from the existing ONNX closure and the five instruction libraries are explicitly loaded in dependency order by absolute path; remaining import resolution is limited to Windows system libraries. No directory scan or automatic backend selection is used.

`labels` contains 1 through 64 ordered `{wire_id, topic_id}` mappings with contiguous wire IDs from `T01`; topic IDs agree with executed labels. `policies` repeats all six component policies. Supported policy IDs are `qwen-json-message.v1`, `single-message-no-truncation.v1`, `grammar-greedy-eog.v1`, `ordered-instruction-topics.v1`, and `closed-assessment.v1`, plus the explicitly bound runtime requirements. Source text is a JSON message with angle brackets escaped; the Qwen assistant prefix closes the empty thinking block. Grammar constrains greedy generation, and the decoder independently rejects malformed, duplicate, unknown, or conflicting decisions. An EOG is required before the output limit. Scores are absent. Semantic uncertainty remains `uncertain`; it is never converted to assessed absence.

An explicit caller resource policy must admit the complete serial composition. The default thread budget remains two; an instruction component can use eight only when the profile and caller policy explicitly admit eight. ONNX components remain at two. Existing worker deadlines, cancellation, and parent ownership apply to loading and decoding; context and sampler are destroyed after each call, and unloading destroys model and runtime handles. No prompt is logged.

The bridge lifecycle test in `tests/instruction_runtime_lifecycle.cpp` includes the production bridge with an in-memory API fixture. Compile it as a standalone C++17 executable with the same pinned headers and the static MSVC CRT (`/MT`, `/EHsc`). It checks cleanup after EOG, decode failure/exception, token/output limits, and cancellation without loading runtime DLLs or model files.

Runtime library identity uses volume and file IDs, so extended and short path spellings cannot cause a false mismatch or weaken the binding to a basename. The model loader receives an explicit single-file split list; a GGUF declaring additional splits is rejected instead of discovering companion files. Preparation failures emit only fixed numeric stage codes on stderr. Native codes 100–108 identify DLL load, 200–208 identity, 300/310 exports, 400–403 CPU backend initialization, 500 model opening, and 900 a caught exception. No path, model response, source text or exception string is logged.
