# Dipsy account passkeys v1

This policy is normative for the seven account-passkey v1 profiles governed by ADR 0061. The JSON Schemas define the closed wire shapes. The OpenAPI document defines paths, methods and results. A conforming implementation must also verify the state, time, cryptographic and authority rules below.

## Deployment and parsing

The production relying-party ID is `dipsy.fi`. The only production browser origin is `https://account.dipsy.fi`. Serve the browser ceremony, protected account APIs and Entra callback from that origin. Use top-level presentation, deny embedding and omit permissive CORS. Check the exact browser Origin and a fresh context-bound CSRF value for every browser POST. Also check WebAuthn client data against the fixed origin. Refuse cross-origin or framed ceremony data. The account page creates the random browser-context CSRF value and serves it only to the owned browser document. The operating environment pins the RP ID and origin. An isolated QA environment pins its own RP, origin, credentials and trust. Values in a request or browser return cannot select a deployment. [WebAuthn RP and origin rules](https://www.w3.org/TR/webauthn-3/#sctn-validating-origin)

Enable the new routes only for the exact compiled profiles and approved environment. Check the profile on every request and fail closed on unknown or mixed profiles. Browser list requests carry the profile in `X-Dipsy-Account-Passkey-Profile`. The existing paths retain their own profiles. Do not accept version negotiation by following a mutable profile reference or deriving one from a value in a key or signature.

Enforce UTF-8, the declared byte sizes and closed schemas before semantic validation. Refuse duplicate or unknown members in the Dipsy envelope and the native client-data profile. Refuse noncanonical or padded base64url, invalid date encodings and unsafe integers. For browser client data, require the expected security fields and reject duplicates. Ignore additional non-security members and retain the original bytes for signature verification. [Chromium client-data guidance](https://chromium.googlesource.com/chromium/src/%2Bshow/refs/heads/main/content/browser/webauth/client_data_json.md) Re-encode decoded base64url to check canonical form. Credential IDs are 1 through 1,023 bytes. Client data is at most 3,072 bytes. Registration attestation is at most 8,192 bytes. Require strict CBOR and DER where the selected WebAuthn value uses those encodings. Reject trailing data and duplicate security fields. Use the current server time at each authorization point. API deadlines are UTC seconds with three decimal places. JWS deadlines are integral NumericDates. A deadline expires when reached.

Native requests use an exact `{request, proof}` body. Browser mutations use the same-origin context. Public errors use the closed schema and the code-to-HTTP mapping in the associated profile. Do not echo the request, identities, raw evidence or reasons that disclose a private record. Give a customer with an actionable refusal access to a minimized, opaque support reference outside sign-in. A verified account context can associate the reference with the refusal before a hosted session is issued. Keep anonymous responses uniform and reveal account-specific details only after Identity verifies the requester. A transient upstream failure can use the separate temporary-unavailability response. Use no-store responses for ceremonies, credentials, support references and authenticated account state.

## Native installation proof

Resolve the exact public P-256 key from the authoritative source operation or registered installation. Before Connect, the confirmed setup source already pins the intended provisional key. Begin does not register that key or grant installation authority. A caller supplies the original source operation ID and the exact browser ceremony ID. The source kind maps to the browser ceremony's initial or registered source. Compute the supplied `binding_digest` as lowercase hexadecimal SHA-256 of the RFC 8785 bytes of the published browser-ceremony v1 binding, with the same semantics as its proof-bound read. The server resolves that authoritative record and captures its current admission generation and independently verified customer. The requester does not supply the generation. A new caller-supplied key, key identifier or account reference cannot replace a pinned one.

The challenge endpoint accepts the exact operation and the closed inner request it will authenticate. Issue 32 unpredictable bytes, store the pending challenge with the SHA-256 digest of the RFC 8785 inner request, expected key thumbprint, scope, purpose, generation and original 60-second deadline. Return the same non-authorizing shape for a closed but inadmissible target. Such a target has no usable challenge. Rate-limit challenge issuance and completion. [JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785)

The signing input is the proof profile's NUL-terminated domain followed by its seven fields in order. Prefix each field with its four-byte unsigned big-endian length. Use the fixed uppercase method, exact path and audience declared for the proof purpose. The digest and RFC 7638 thumbprint enter as 32 raw bytes. Verify the corresponding ES256 P1363 low-S signature and derive the `ik1.` key ID from the first 16 raw thumbprint bytes as unpadded base64url. Check the expected purpose, digest, key, generation, unused challenge and original expiry. The authorization transaction consumes that proof and applies the relevant operation rule. Proof requested before the Hello prompt does not stand in for the fresh enrollment-finish proof.

## Enrollment and same-account replacement

1. Begin requires the current proof-bound source, explicit customer intent, an admitted native application operation and recent verified Entra evidence for the expected enabled customer. The accepted evidence includes silent reuse when Entra supplies a recent signed authentication time. Verify the signed ID token's issuer keys, audience, tenant, nonce and immutable subject. Persist only the verified facts and original deadlines needed at commit. The session, token and source operation retain separate expiry checks. The browser redirect and the setup locator convey no authority.
2. Pin the subject handle, source session and generation, intended installation key, enrollment and attempt IDs, RP ID, installation-held initial-access nonce, challenge and authorized action. Generate a random RP-scoped 32-byte handle for a new account rather than exposing Entra identifiers. Generate the display label within the schema's neutral format. Begin leaves a pending attempt. Exact prepare reconciliation can return the same live attempt and options. Changed meaning conflicts. For exact retries after cancellation or expiry, require a deliberate new enrollment ID and current authority.
3. The installed sender calls Windows Hello through its restricted foreground broker. Use the selected local Windows Hello path, discoverable ES256, presence and user verification. Use the profile's exact native client-data origin and the server-issued challenge. A customer who cancels, defers or lacks a usable local authenticator can resume setup without local authority from this attempt. Show the operating-system permission recovery route where appropriate. The packaged app observes the actual Hello result.
4. Finish binds the **exact** client data and attestation bytes in the installation-signed request. Verify `webauthn.create`, the authorized native origin, the challenge, the RP ID hash, credential ID equality, presence, user verification and the approved P-256 COSE public key. Require a none attestation object with empty attestation statement for this profile. Refuse an authenticator backup-state bit set without its backup-eligibility bit. There is no authenticated app, hardware or gesture attestation, and the new credential does not sign the creation response. The Provider's remote proof covers the exact response with the admitted installation key. Product observes and verifies the local ceremony.
5. Under the transaction locks, recheck the enabled directory account, source operation, source session, generation, intent and current token validity. Require a signed authentication age within the inclusive interval 0–300 seconds. Use the signed authentication time, never callback arrival time or a general token clock tolerance to extend eligibility. At the original attempt deadline, refuse. Bind the entire response to the attempt, including equality of its credential ID to the bytes in authenticator data. Atomically create the unique `(RP ID, credential ID)` association and consume the enrollment authority. A finish call that commits returns 201. A concurrent finish cannot register another credential. A consumed finish remains closed.
6. The dedicated receipt read uses fresh installation proof, exact account and operation binding and current recovery authority. It returns the same committed result, with 200, before the earlier authorized recovery deadline or 1,800 seconds after commit. Treat a revoked or expired scope as closed. A receipt contains no binding, hosted session or initial local access. Issuing a receipt does not change any attempt or source lifetime. Cancel consumes a pending attempt and returns its cancellation state. Use the exact credential-removal operation for a committed credential.

A new or replacement account credential uses this enrollment operation for the independently verified same Entra customer and intended installation. Possession of only a computer key, an email address or a lost result cannot establish account identity. Process protected installation-authority recovery under its separate ADR 0060 purpose before any action requiring that authority. The routine account-passkey session cannot stand in for its Entra step-up. An enrollment that commits before Connect introduces a hosted credential only. A customer still explicitly decides Connect for the particular resource and installation.

## Hosted sign-in and exact removal

Begin a browser assertion with a random one-use 32-byte challenge, maximum 120 seconds, bound to the browser context, purpose, RP and any expected customer stored in its exact ceremony. Supply discoverable credential options. Finish verifies the `webauthn.get` type, exact origin, challenge, RP hash, user presence, user verification and the ES256 assertion signature over authenticator data and the SHA-256 of the original client-data bytes. A true `crossOrigin` field or a `topOrigin` identifying a framed ceremony is refused. Require the discoverable user handle to match the credential record and any expected customer. Reject an unknown, revoked or mismatched credential without revealing which predicate failed publicly. Check directory status when issuing the session. [WebAuthn authentication verification](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion)

The hosted and local verifiers accept valid zero counters and positive jumps. Neither expects a consecutive counter or synchronizes counters with the other. A non-increasing positive count may emit a minimized anomaly signal without becoming a substitute for signature and authority checks. Reject a backup-state bit set without backup eligibility. [WebAuthn assertion verification](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion)

Issue the established host-only customer cookie as Secure, HttpOnly, SameSite Lax, Path / and with no Domain attribute. Set the method to `service-passkey` and store the verified time, actual credential reference and fixed expiry no later than 1,800 seconds after verification. Session rotation, reuse and activity do not slide that deadline. Browser responses contain only the closed outcome and deadline. A desktop return wakes the existing proof-bound operation read and cannot authorize an action by itself.

The current-session onboarding paths can admit the new method only through an explicit updated policy. They still require the expected account, exact intent, native consent when required, organization role, current entitlements and independent installation proof. Preserve the 300-second intent lifetime and separate 60-second installation proof. Existing protected installation recovery, paid actions, delegation and reissue keep their authorized methods. Method evidence must reflect what was actually verified.

An authenticated credential inventory returns neutral labels and account-scoped opaque references. Bind a continuation cursor to that session and inventory scope. Each page carries at most 50 credentials. No real provider identifier, public key or OS inventory is disclosed in the list. Removing a passkey uses a separate removal attempt and fresh confirmation of the exact target and effect. Show if it ends the current session or can remove offline access. For the last or uncertain local credential, explain the offline consequence and offer same-account replacement or recovery before confirmation.

Begin removal records the existing current hosted session, verified customer, target, effect, generation, method, exact purpose and fixed deadline. Use the `session-binding` and `removal-scope` definitions. The former binds the server-held session ID and session generation to the opaque subject handle. The latter binds the exact attempt, subject, session digest, method, origin, target credential, generation, displayed effects and deadline. Compute each digest as lowercase hexadecimal SHA-256 of the RFC 8785 bytes. These objects and evidence stay server-held. For `service-passkey` use a separate challenge and a recent same-account assertion. For `entra-action`, the step-up route follows the existing confidential-client, operation-bound Entra callback. It correlates the same attempt and exact target. Request fresh Entra authentication for the action, verify the signed claims and source expiry and create server-held evidence only. The redirect is to the configured Entra endpoint. No client-returned success flag, token or evidence object authorizes removal. The final POST explicitly confirms the exact named target. Verify and consume the server-held method-specific evidence with fresh age of at most 300 seconds, current account and role, and the original intent and session still valid. Any target, generation, owner or declared effect change requires a fresh authorization. Atomically revoke the selected credential, its derived hosted sessions and their pending authority. Other independently verified sessions retain their scope. Publish the affected local withdrawal. A hosted sign-out ends only its hosted session. Disconnect and OS credential deletion keep their separate meanings.

## Independent local binding, access and withdrawal

The Provider delivers a signed public local-binding record only after matching committed Connect. Brain checks the pinned purpose, exact subject handle, installation and key thumbprint, RP, credential ID, approved public key and monotonic generation. An `active` read requires fresh registered installation-key proof and current exact account authority and returns only the active binding. A `withdrawal-only` read provides the exact known binding digest and fresh proof of its registered installation key. If current directory status allows the check, it can disclose the matching already signed withdrawal even after the credential-derived hosted session ended. It returns only the withdrawal and grants no other authority. The local JWS uses RFC 7515 compact ES256 P1363 low-S. Canonicalize the protected header and payload using RFC 8785. Verify the exact `alg`, `kid` and `typ`, issuer, audience, payload members, purpose and signature for the expected record type. Use distinct pinned signer purposes for binding, initial access and withdrawal. Resolve the expected purpose and `kid` through the immutable account-passkey trust set carried by the verified installed release. The purpose codes are `pb`, `pa` and `pw` respectively. The key ID is `bc1.<purpose-code>.<RFC7638 prefix>`, with unpadded base64url of the first 16 thumbprint bytes. Verify the full thumbprint, unique key ID, exact purpose and key validity at `iat`. Retired keys continue to verify previously issued valid records within the supported record lifetime and cannot issue at or after `retire_at`. A locally known emergency revocation rejects the key regardless of `iat`. Apply additions, retirements and revocations for these purposes through a verified vendor-signed release carrying an immutable manifest with a higher sequence. Reject rollback, unknown purpose and environment substitution. The existing online grant-transition v1 retains its existing purposes. Fixture keys do not belong in a production trust set. [JWS standard](https://www.rfc-editor.org/rfc/rfc7515)

For `binding_sha256` and `withdrawn_binding_sha256`, hash the exact ASCII bytes of the issued compact binding JWS with SHA-256 and encode the digest as lowercase hex. For `withdrawal_sha256`, apply the same rule to the exact issued withdrawal JWS. The input is the three compact segments and two periods, without JSON string delimiters, whitespace or a trailing newline. A decoded, re-encoded or unrelated object does not have the same identity. An authorized read returns the exact issued bytes. Retain the active binding bytes only while enrolled, with full-record cleanup within 24 hours of withdrawal or confirmed deletion. After cleanup, retain only the binding digest and necessary scoped withdrawal until confirmed delivery or installation retirement.

Initial local access is an independent issue operation. Only the fresh successful enrollment and its committed Connect can authorize it. Verify the original nonce, enrollment and attempt IDs, exact installed binding digest and generation, credential and current installation proof. The signature binds those facts and the original verified enrollment and source expiry times. Require `iat <= now < exp` and `exp <= min(source_expires_at, verified_at + 300)`. Issue at most once for that exact connection. General binding reads, receipt reads and retries after uncertain issuance supply no new initial authority. Brain consumes the exact nonce-bound authorization once, in an uninterrupted trusted local enrollment context, before creating any local session. Ensure proof consumption and local session issuance are atomic. After restart, uncertainty, consumption or expiry, require a new assertion.

For subsequent local access, Brain generates a 32-byte one-use challenge independently. It pins the exact locally bound account, credential, RP and separate native assertion origin, verifies the fresh signature, presence and user verification, and checks the 120-second deadline. Entra, Provider and commercial grant expiry do not control this local assertion. An independently authenticated saved-data session permits view, export and selected deletion under its existing policy. New capture and analysis retain their separate grant and grace checks.

A signed withdrawal identifies the exact binding digest and credential, entitled installation and key, subject, RP and advanced generation. Persist the highest observed generation and exact record digest, and invalidate affected local sessions before acknowledging the exact withdrawal over fresh proof of that registered key. A withdrawal acknowledgment can use the same authorized withdrawal scope without an active credential-derived session. Duplicate evidence at the same generation is idempotent only for the same verified record. After restart, reject stale or conflicting bindings and older withdrawals. Only independently authorized new binding state can advance the local authority. The Provider retains the scoped delivery record until durable acknowledgment or installation retirement. Remote changes can take effect on a disconnected installation only when it learns the authenticated withdrawal. Separate OS key deletion is outside this receipt.

## Directory state, retention and recovery

Use the verified tenant and immutable directory object for the two-field status lookup. Every hosted credential and session issuance and protected disclosure, stream frame or write needs a current status decision. Capture the durable per-principal observation fence and original time at lookup start. Accept a positive only under the current fence in observation order, preserving its original timestamp. On disabled, deleted, denied or malformed status, invalidate the cached positive and advance the fence atomically. Confirmed disabled or deleted status also revokes the principal's hosted sessions. Only transient errors can reuse a prior enabled result. The age must be nonnegative and strictly below 300 seconds. Unknown or stale status refuses. A delayed result, restart, cache hit or restore cannot renew a positive. Re-enablement requires fresh enabled status under the new fence and a new session.

Keep the external lookup outside business locks. For writes, serialize on the same durable fence used by invalidation and hold it through the authorization commit. Use the existing organization's and workflow's lock order before the applicable Identity state. Invalidation records its wakeup with the durable change. Recheck the current status and session generation before protected disclosure and stream frames. Existing saved-data access has separate authority and does not poll directory status. The directory decision applies to hosted access. Entitlement termination and account closure follow their distinct decisions.

Use the catalog classes for this family with the record-specific retention rules below. Keep the minimum credential record while enrolled. Remove superseded full credentials from live stores within 24 hours of withdrawal or confirmed deletion. Remove superseded or expired status details within 24 hours of replacement or expiry. Close attempts at their earliest applicable expiry, cancellation or use. Remove closed attempts and expired receipts within 24 hours. These cleanup limits cover online copies and operational exports. Cleanup does not extend authority. Retain effective revocation while earlier authority can still be used or recovered. Retain first-release identifiable security transitions and actionable failures for up to 30 days from the event across live data, queryable copies and exports. Aggregate routine checks. A minimized case may survive longer only for a documented active purpose with an owner and review date. Keep restricted backup copies within the deployment's approved finite recovery deadline. Restore original deadlines and reapply later deletions, withdrawals and revocations before reopening protected traffic. Remove expired audit and working entries and keep access closed when the restored state cannot be verified.

Keep private keys, PINs, biometrics, raw tokens, raw assertions, creator or fan data and local sessions out of hosted durable evidence and logs. The customer can reach support outside sign-in and obtain human review after account verification. Keep unverified account responses generic. Release qualification verifies the actual recovery horizon, disposal, human-review path and customer wording against the approved design.

## Compatibility and rollout

The seven profiles are additive. Existing session, installation-recovery, entitlement and pairing profiles retain their conditions. Enable each new profile only for a consumer that implements and advertises it. The first enrollment uses the existing enabled Entra routes, including Microsoft personal through the hosted picker.

Freeze the candidate by exact commit and contract and conformance manifest digests. Product and Provider each verify the same vectors under their independent implementations before promotion. Bind the release trust set and accepted trust-transition sequence to the deployment and consumer verification. The reconstructable fixture keys are for tests only.

Preserve committed credential withdrawal and directory revocation during rollback. Block affected protected operations until the selected service can enforce them. A disconnected installation verifies saved-data access under its last accepted binding and any known withdrawal. The production rollout requires its own release decision.
