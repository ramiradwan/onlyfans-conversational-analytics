# Desktop setup coordination

[ADR 0050](adr/0050-desktop-onboarding-and-browser-tasks.md) assigns the local coordinator to Brain. `shared/desktop-onboarding/schema-v2.json` defines the current closed snapshot and unchanged v1 command document. The historical `schema.json` remains unchanged. `shared/browser-tasks/schema.json` defines the separate browser observation and task payloads. Desktop and browser requests require their own scoped admission.

A desktop setup root survives replacement presentations and the configured restart. Opening browser access creates no installation source. An explicit account command selects the bounded source context through the existing installation owner and freezes that selection in its accepted operation. Configured activation selects the current installed authority independently of an old browser presentation.

Commands carry a UUID, journey, presentation generation, projection revision and scope digest. Brain rechecks these under its writer transaction before accepting work. An identical duplicate reads the original receipt. Startup continues the original accepted operation. The service automatically retries domain-approved account recovery at bounded intervals, preserving the accepted source, key and deadline. It does not create new commands or open browser windows. New runtime mutations still require current operator authentication.

Reads perform no protected work. Event streams subscribe before reading the complete projection and retain invalidations received while busy. Local readiness requires verified installation, account, configuration, enrollment and pairing. Full readiness additionally requires activation and analysis admission; missing activation never withdraws completed local setup or dashboard access.

[ADR 0054](adr/0054-consolidate-onboarding-coordination.md) consolidates commercial and analysis readiness in the native snapshot. Its `analysis_readiness` projection discloses the exact account and closed readiness value only to the authenticated creator. Unknown and unauthorized views carry no readiness value. Settings and Dashboard subscribe to the same desktop store; they have no separate readiness fetch or polling controller. The standalone capability readiness GET is retired; explicit code redemption remains. Owner commits invalidate the stream, known grant boundaries wake it for a fresh read, and the existing bounded stream wakeup recovers observations. GET deadlines also bound response-body reads. Readiness enrichment changes no command hash inputs or admission guards.

The existing authenticated browser-surface channel uses `ofca-browser-surface/v2` with a nullable `history_error_code`. Only `identity_required`, `unsupported_revision` and `history_unavailable` cross this boundary. The signer owner supplies an unsupported-revision observation for its current authorization; raw errors and signing material remain in Agent. Missing browser observations leave site permission unknown. Complete saved coverage stays visible independently of upstream acquisition failure.

The native setup page opens the dashboard once after a current connected projection reports completed local setup and the existing local authentication owner confirms the operator session. Disconnected or unread state cannot trigger navigation. Optional activation does not delay this transition.

Browser observations describe only the admitted extension participant's coarse state. Each admission pins its extension, instance, epoch, disclosure and account/consent generations. A replacement task entry fences prior profile admission without asking the customer to retrieve a link. Observations cannot grant consent, collection permission, pairing or operator authority.

Brain records ceremony coordinates before a single prepare send. Subsequent attempts proof-read that exact operation. The Provider's domain result is delegated to its existing local owner. Neither browser callbacks nor global readiness facts resolve an uncertain reserved commercial operation. Ceremony journals contain no Provider credentials, grant bodies or redemption continuations.

Completed and refused operations expire at their original deadline. The next explicit command removes them and their dependent ceremony and activation coordinates. Unresolved operations remain available for reconciliation. A limit of 128 bounds command creation without blocking fresh native presentation admission or reads. Retention does not renew the underlying domain's proof, source or delivery lifetime. Expiry without a verified result remains uncertain. Browser task admissions have their own original deadlines and cleanup.

The coordinator is composed separately into the restricted and configured boot graphs. The browser wizard and its launcher, route aliases, return controllers and extension navigation protocol are removed. The complete installed setup, enrollment and pairing matrix remains a release qualification requirement.

The separately bundled `frontend/onboarding/` entry renders the same projection in both boot graphs. Its build rejects dependencies on dashboard, analytics, runtime WebSocket and Chrome modules. Native entry consumes the backend-issued presentation; it does not choose a UI from configuration filenames. A launcher-only current-presentation check lets browser returns focus the live window without revoking its task.

`frontend/browser-tasks/` is a separate lightweight entry. Only that entry imports Chrome adapters. Its port admits the exact top-level helper document, task generation, pinned extension and original operation. A new generation fences the previous port. Failed discovery means unavailable; it does not prove that the extension is absent. Installation refreshes only a matching helper document. Both setup entries and the dashboard's named manifest entry are mandatory package inputs.

A live helper sends a scoped liveness message every 20 seconds to prevent an idle Chrome worker from closing the task port. The extension rechecks its tab and fixed expiry before acknowledging; liveness does not read account data or renew admission. Missing acknowledgements close the connection. On disconnect the helper reads Brain's admission before choosing between an unavailable extension and a replaced task.

A completed authentication payload withdraws its ceremony entry. The helper accepts that read-only projection only with the original task, admission, scope and deadline; extension attachment and paired dispatch still require a complete launch payload. An authentication failure remains attached to its original command until a matching authoritative admission or review supersedes it. A task-ready event received during a native task read is coalesced for that same explicit launch intent; dispatched or uncertain work is never automatically relaunched.

The native renderer retains an explicit browser launch for at most three minutes and no later than its task deadline. Only a matching authoritative completion, current admission or withdrawal returns focus once through the existing guarded window command. Generation, journey and child changes fence it. Unknown outcomes do not focus the window. Chrome helpers no longer automatically open app links; an explicit app-link recovery remains available.

After its acknowledged observation or completed task, the helper sends a closed `finish` message for its existing task and generation. The extension rechecks the admitted sender and closes only that exact document through the existing scripting permission, with an in-document fixed-URL, top-frame and original-deadline guard. It never removes a tab by ID alone. Cleanup acknowledgement, disconnect or a five-second timeout releases the port without changing the factual completion state; browser refusal to close leaves the completed surface available.

The initial desktop/extension entry source survives restart. Extension-first attachment checks saved journey, draft and launch/adoption evidence. Task adoption and the stable extension-instance identifier are presentation metadata; neither authorizes account selection or collection. Account observations are emitted only under current Full consent and site permission, and Brain reconciles only their original accepted task. The existing explicit cross-device receiving route retains its domain checks.

Authentication requires an explicit native or scoped-helper action, the accepted creator account and the release-pinned Provider origin. A consumed native task entry carries one generation-only launch intent, spent before helper startup. Only an idle exact task can continue it; reload, reconnect, changed scope and uncertain outcomes require another explicit action. Pending native dispatches recheck their original launch owner after each response. The extension adds only Chrome's `identity` permission and calls `launchWebAuthFlow` with the exact ceremony entry. Its return parser accepts only the registered path and exact ceremony/attempt correlation. Chrome closure, rejection and worker shutdown cause an uncertain notification; Brain proof-reads the original operation. Neither the callback nor helper presentation establishes completion.

The extension retains at most eight authentication correlations in `browser_auth_attempts_v2`, uniquely keyed by local task ID, with no entry URLs, credentials, returned URLs or API errors. Each record is bound to the original task, participant, selected creator and ceremony and expires at the earlier task/ceremony deadline. Successor tasks may share a parent ceremony without sharing a journal entry, active flow or callback outcome. Reads and alarms discard expired records; startup recreates cleanup alarms without opening windows. A generation-only helper reissue retains the full binding; changed scope under the same task ID is refused. A live flow or received callback is reused; a lost flow requires another explicit action. The ordinary-Chrome fallback opens the same ceremony with a nonauthorizing presentation fragment and returns status checking to the desktop.

For an explicitly requested authentication task after pairing, Brain rechecks the current desktop admission, operator, operation and selected creator before sending a closed `session.control` browser task through one unambiguous reporting companion pin. Dispatch rotates the browser-task admission, retiring any old helper without minting another entry credential. The extension checks its current consent, task participant and pinned account before opening. Paused Full uses the existing control-only channel without a platform account read, storage unlock or capture lease.

The session retains at most eight task correlations to the original deadline or channel close. Acknowledgements contain only task/generation and ceremony/attempt correlation; they cannot carry credentials or establish a domain result. Five seconds without an acknowledgement means delivery is unconfirmed. An unreachable channel allows the native helper entry path; an uncertain delivery never automatically opens another window. Reconnect and status reads never redispatch tasks. Late accepted notifications only proof-read the original operation while its task admission is current.

Native browser navigation and capture controls use Brain APIs and closed destinations. Activation and pairing callers use the scoped coordinator client, including both desktop and operator request contexts for runtime mutations. The consumed native entry retains only its presentation locator in tab storage; cookies and operator authentication still establish authority. The native controls do not use Chrome APIs. Manual pairing remains an explicit recovery action under Connection options, with independent code comparison. A browser with a saved pin reports that fact; explicit replacement rechecks the exact saved pin, task, creator and consent before local disconnect and connection to the current desktop.

The runtime setup page uses the existing WebAuthn registration and sign-in owner, with the unchanged `bridge.localhost` relying party and local origin. A status read never invokes a passkey ceremony. Registration or sign-in requires an explicit action in the desktop window. The same-origin session-state response includes the current CSRF context only for an authenticated session, allowing one read to recover a lost completion response without replaying enrollment. Its closed enrollment validator is generated for the isolated setup bundle.

An authenticated native `browser.pair` command reserves a random pairing identity and a deadline of at most five minutes before opening the existing pairing service. Recovery reuses the same identity, private key and deadline. The task helper starts only that accepted intent and forwards the independently received extension-port code once. It receives neither Brain's comparison code nor operator credentials. Brain rechecks the exact task generation and current operator inside the confirmation or decline transaction before the existing constant-time comparison can commit a pin. Helper responses report checking; only observation of the exact admitted pin completes the operation.

Brain's pin commit precedes the extension's durable authenticated connection. A helper that started pairing retains its port until both Brain completion and the exact task-bound `pairing-completed` extension receipt. That receipt follows the committed connection and local reconciliation; it cannot complete Brain's operation. Lost comparison replies retain the same bounded handshake without resending comparison or creating another pair. Reloading completed work never starts pairing.

Pairing reservations share the terminal operation's bounded retention; they contain no pairing keys or codes. Request authority remains in memory until completion, expiry or shutdown. After restart, a pending comparison requires an explicit authenticated native reconciliation. A committed pin can be recovered without repeating the confirmation. Expired, declined or revoked attempts are terminal and do not open another window automatically.

The extension's Full entry now records only a scoped presentation choice and offers desktop acquisition or an explicit app link. Preview keeps its complete browser flow. Dispatch, transport reachability and window focus cannot confirm adoption; the extension reads the matching desktop browser-task acknowledgement for its current workspace, disclosure and instance. The Full choice survives browser restart in the existing workspace draft, without creating consent or automatically reopening the app.

Only an admitted access task opens the compact Full consent and permission presentation. Its single session record expires at the original task deadline, is cleared when its helper closes or the worker restarts, and cannot outlive an in-flight open/close race. Restart does not restore a task from session storage without a new helper admission. A declined Full review retains Preview. There is no extension Full progress rail, normal-route comparison code, or hosted wizard navigation. Setup-code entry remains available only through the deliberate receiving entry.

Authenticated desktop permission and terms-review controls create `browser.access` operations through the same coordinator. Each operation reads only its own browser-task observation for the accepted creator; a previous ready observation cannot finish a new repair. Initial setup operations retain their original domain owner across configuration restart. Native launch never navigates the extension tab into a browser-rendered dashboard.

Setup recovery belongs to Brain. Startup resumes accepted operations using their original installation key, account, association and deadline. Interrupted enrollment proof-reads its original receipt and recovers verified grants without asking the user to handle a recovery package. It never submits a replacement claim, changes accounts or renews the original deadline. Missing keys or a required sign-in remain explicit authority failures; there is no package-entry form or endpoint.

The separate `frontend/setup-code/` entry receives cross-device setup. An explicit native action opens Chrome at a fixed fragment landing, consumes a short-lived single-use code and establishes a receiving-only cookie. This browser session is bounded by its native presentation and source deadline. It cannot call native commands or act as a general browser task. Provider form posts remain restricted to the release-pinned setup destination; only this explicit transfer relay retains `POST /provisioning`. No retired `GET /provisioning` page or script alias is served.

Native presentation recovery is distinct from domain recovery. A launcher-only refresh is bound to the renderer's former presentation generation and its saved journey. The immediate successor is retained for bounded lost-response recovery; replay issues a fresh one-use entry for that same generation and original expiry. Any unrelated active or pending presentation refuses replacement. Read-only coordinator projections remain accessible through their own scoped admission when an obsolete operator cookie is present; protected commands still require current operator authority.

The helper reads its exact task every two seconds while connected, backing off interrupted reads to fifteen seconds. It advances only on Brain's task projection. A successful read after a transient outage restores the last valid task presentation without replaying authentication or pairing. A recent consumed native launch may invoke the fixed journey app link once while its document is visible and focused. Hidden, late or manually opened helpers cannot steal focus. The app-link prompt remains platform-owned. The Settings permission-return action is separately bound to the explicit request, creator, journey and presentation; native focus is refused when another application owns the foreground.

Expired sources are classified through the saved-workspace owner before an explicit account command can admit a new context. The classification generation, selected installation/key/account and outstanding work are rechecked in the admission transaction. The original source coordinates and deadlines remain unchanged. For initial enrollment, only a validated `found` ceremony snapshot with the exact original binding and `domain_status=unavailable` establishes expired non-commit. A top-level unavailable response, transport refusal or elapsed local deadline does not. The owner stops an idle wait before recording that proof; completing work and completed live or retired evidence refuse a delayed terminal write. Confirmed Provider expiry can allow explicit continuation before the longer local presentation expires; desktop clock skew cannot override that exact terminal fact. Uncertain initial preparation or completion can resume through the existing exact recovery tombstone within its original recovery deadline, without issuing a browser session or a replacement hosted operation. Completion of that exact recovery resolves its original uncertainty records without extending their retention. Confirmed completion still requires the current verified account grant tuple; a completed installation alone does not establish account readiness. Missing or unconfirmed outcomes remain unknown.

Browser observations may carry bounded display name and username metadata from the exact currently observed creator. These optional labels never replace identity or consent authority. Native account review compares the label's creator ID with the selected decision. New passkey registration uses a readable label from a completed matching installation/key/account ceremony, with an account-ID fallback; the credential user handle, principal, relying party and verification rules remain unchanged. Ambiguous or malformed historical labels are ignored. Passkey status errors distinguish transport, admission, refusal and malformed response without inferring enrollment.

The Provider owns absolute delivery-recovery challenge expiry. Product validates the bound purpose and digest and a lifetime of at most sixty seconds, counting the entire request round trip and signing against a monotonic deadline. Desktop UTC skew no longer rejects a fresh recovery proof. Wire contracts, Provider enforcement, expiry and replay protections are unchanged.
