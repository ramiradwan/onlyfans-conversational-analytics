# ADR 0050: Coordinate setup in the native desktop application

- Status: Accepted.
- Decision authority: Product owner, through approval of the desktop onboarding implementation plan.
- Supersedes: ADR 0047's single browser workspace and extension-owned Full presentation; ADR 0045's direct Chrome access from Bridge; ADR 0048's browser return presentation. ADR 0049's durable ownership, fencing and uncertain-outcome requirements remain authoritative.
- Amended: 2026-11-08, 2026-11-12 (proposed: push-based end of the sign-in popup), 2026-11-14 (wording: the sign-in popup may open on a local waiting page first), 2026-11-17 (browser setup progress survives presentation expiry)

## Decision

Bridge is one Windows Tauri 2 application. Brain owns one durable setup coordinator. Required setup progresses through Browser access, Account connection and Finish setup. Verified installation/account binding, enrollment and pairing admit the dashboard under existing local authentication. Commercial activation is a separate resumable dashboard/Settings task; missing or uncertain activation never makes completed local setup incomplete. Existing capability admission still governs Full analytics.

The native host owns its fixed-path Brain child, window, tray and single-instance activation. It verifies the listener's address, PID, image and user before admitting its fixed local origin, `http://bridge.localhost:17871`. Process exit invalidates that admission. Exit 75 permits one controlled configured restart; ordinary failure never creates a restart loop. Close hides the window; Quit stops the owned backend. No login autostart is added.

Preserve the configuration-selected boot graphs described by ADR 0017 without promoting its other proposed behavior. Unconfigured setup imports neither runtime settings nor the dashboard/analytics graph. Publish complete configuration atomically and never infer recoverability from malformed present configuration. Native possession is not operator authentication. Local WebAuthn retains its relying-party identity and origin.

Expose only declared purpose-specific native commands, with an explicit Tauri application command manifest and exact window/origin capabilities. Renderer inputs cannot select executable paths, profiles, arbitrary URLs, shell commands, filesystem contents or HTTP targets. External pages receive no native authority.

Admit the exact configured application paths used by Bridge's client router: `/`, `/inbox`, `/analytics`, `/graph-explorer` and `/settings`, alongside the isolated onboarding entry. Client navigation within the owned document retains its native presentation commands. The Rust document check and Tauri capabilities agree on those paths; browser helpers, setup-code documents, API endpoints and unknown paths remain excluded. The live owned-child admission, exact main window, operator authentication and command guards still apply.

The main window uses the app's styled header in place of the OS title bar. One header contains the app name, a noninteractive drag region and accessible minimize, maximize/restore and close controls. Startup and failure documents retain those controls. Window presentation commands remain separately scoped to the owned window and exact packaged shell or admitted local document; browser tasks gain no native authority. Status copy states the observed status and, where useful, a simple next action.

## Browser tasks

Chrome is the supported browser. Preview remains extension-only. Full intent is not collection consent. Consent, governed instruments, browser permission and permitted account observation stay with the extension's existing owners. A browser helper is a task surface with no overall wizard; it alone imports Chrome adapters.

Separate desktop presentation admission from browser task admission. Bind each to its role, journey, task when applicable, generation and fixed expiry. A replacement presentation fences its predecessor while retaining accepted work. Identifiers and app links are locators, not authorization. The `ofca://onboarding/?journey=<uuid>` app link uses Chrome's canonical root path and carries no account selection, credential or protected decision.

Before pairing, the verified native launcher issues a single-use task entry; Chrome supplies the existing top-level extension sender admission. Never copy a WebView cookie into Chrome or add an unpaired command socket. Browser tasks last at most 1800 seconds, bounded by their parent and operation deadlines; entry links last at most 300 seconds. Reads do not extend either. For the wrong profile, the customer switches profiles in Chrome and opens a newly issued task link. Reissue fences the old admission, preserves the protected operation and grants no account authority. The host does not inspect Chrome profile files.

This is an explicit additional exception to ADR 0047's launcher-only URL admission rule: a local browser-task entry may carry one opaque credential for its exact landing and task. Persist only its digest, consume it once, and remove it from the URL immediately. It cannot authenticate a general Bridge session or authorize a protected decision.

The browser participant must match saved Full intent and workspace evidence on extension-first entry. Desktop-first attachment requires the explicit browser-access action. Merely opening a helper does not choose a creator. The install event attaches to an existing admitted helper rather than creating another Full wizard.

After pairing, closed browser tasks and bounded acknowledgements use the authenticated companion session. Paused Full retains its control-only channel without capture or storage unlock. Pairing still requires Brain's constant-time comparison against the independently delivered extension-port code, scoped to that exact task. Existing manual comparison remains an explicit recovery route.

## Hosted ceremonies and durable coordination

Provider authentication, exact creator approval and commercial confirmation stay in focused hosted ceremonies. The extension opens the exact ceremony entry in a popup window it creates, in system-browser presentation. The extension may first open that popup on its own local waiting page and then navigate the same window to the exact ceremony entry, so an attempt still has one popup. The waiting page carries no ceremony and no authority, and every write still starts only from the explicit click. The hosted page ends on its own completion screen and never navigates to the extension's return URI. A popup is used because a Provider's sign-in can hand off to its desktop application through a custom-scheme link, which the browser's extension authentication flow refuses. There is no extension return. The extension reads no tab URL and gains no permission for sign-in. Removing the popup while it is opening is closure. A failed popup creation is an uncertain outcome, never closure. The extension removes the popup itself when its browser task ends or expires, and that removal is never closure. Sign-in has no ordinary-tab route. Without an extension, the helper offers the extension's install instead. No Provider cookies, identity tokens, licenses or redemption continuations travel through the extension. Brain's proof reconciliation of the underlying operation alone settles the outcome. The cross-plane ceremony profile is owned by the canonical contracts repository; local presentation and browser task schemas remain Product-owned.

The ceremony result adapter requires a new, separately domain-separated installation-key proof profile. Existing browser-only activation reads and redemption proofs are not repurposed. Its activation result returns only the already committed, exact installation-bound `clr1` continuation within its original lifetime; it never mints or renews authority. Provider session cookies remain in the browser that completed authentication. The extension receives no return from the ceremony.

The sign-in popup closes as soon as its browser task ends, by push rather than by polling. Every push is a notification without authority. While a sign-in task is open, Brain holds the Provider's ceremony outcome wait, and each frame starts Brain's existing proof reconciliation. Only that reconciliation ends the task. Brain then pushes the task's end to whichever route opened the popup. The desktop helper receives a content-free invalidation on a scoped event stream under its existing browser-task admission, re-reads its task and finishes it as before. A paired companion session receives the closed control `browser.task.end`, carrying only the task ID and admission generation. Brain sends that control only on a session that advertised support for it during that session, so an extension that did not advertise it never receives it. An older Brain answers the advertisement as an unknown method, and the extension keeps its earlier behaviour. The extension ignores an end that does not match an active task and admission generation, and it removes the popup without recording closure. When a session advertises, Brain also sends the end of each unexpired task it had dispatched to that same pairing, and no other. The extension keeps the popup's window in session-scoped browser storage, apart from its attempt journal, so a restarted extension worker can still remove it, and the desktop helper re-attaches once to finish. A helper tab closes itself whenever its task ends, whatever the outcome, once its outcome has reached the desktop, which shows it in place. Opening a task's browser step prefers the paired session, then a live helper for that task, which is focused, and only then launches Chrome. A paired session receives only the task purposes it advertised, and pairing confirmation always uses the helper. Bounded reads remain only as a fallback while a push channel is unavailable. No extension permission, manifest key or `externally_connectable` match is added.

The product has not launched and has no existing users. Replace superseded onboarding admissions, routes and controllers without compatibility adapters. The corresponding Contracts and Provider decisions explicitly retire their old-client support clauses. Preserve domain authorities and restart/recovery behavior used by the replacement.

New ceremony records require individual retention classifications: expiring contexts and proof challenges, bounded notification correlations, unresolved worker outcomes, committed commercial authority and security events do not share one deletion timer. Existing domain retention remains authoritative.

Local task admission records are presentation working state: delete completed, cancelled and expired task records at their original admission deadline, and delete their unreferenced retired presentations. Preserve accepted or uncertain work for domain reconciliation. Task-creation limits must never prevent a fresh native presentation from reconciling existing work.

Retain the latest admitted browser-access observation as setup progress for its exact journey and installation key, independently of task and presentation expiry. This display evidence grants no browser admission or account authority. A newer observation for that key replaces it, including consent withdrawal, permission loss or sign-out. A missing or changed installation key invalidates it. An old task cannot bind that progress to a replacement key. Expired account decisions return to the sign-in choices on Account connection while browser setup remains established. Presentation renewal and reads never start protected work. The next explicit sign-in uses the existing authentication route and requires a fresh live decision before connection.

A live confirmation and its outcome wait follow the original server decision deadline across local presentation replacement. An explicit account connection refreshes only an unprepared local initial draft within command admission. It never extends a prepared source, customer session or server decision.

Once a known ended decision returns to sign-in selection, untouched setup performs no periodic reconciliation or proof reads. A frame, expiry, changed fact or explicit command still wakes the coordinator immediately. Failed live waits and uncertain reconciliation use bounded recovery delays of 15, 30, 60 and then 60 seconds. Wait eligibility and confirmation diagnostics record value changes only.

Ordinary Provider ceremony replacement follows Contracts ADR 0060. The local ceremony owner retains the exact predecessor, one immutable successor reservation and the independently verified successor row. A successor changes only the correlation attempt, never the original source, installation, customer scope or fixed source deadline. An unavailable successor read is not rollback; existing committed domain results take priority. Installing a verified successor atomically invalidates predecessor-scoped authentication and decision projections and retires obsolete browser tasks and commands. Proof reads and stale callbacks cannot adopt a different lineage; an interrupted send is reconciled by reading the exact reserved successor and never by automatically sending another replacement. A reservation is not permission to open Chrome or to submit an authentication choice. Retain the lineage through the original source deadline, without expired entry locators. For account connection, the existing local sign-in command admits a closed, mutually exclusive replacement variant: auth.select with replace_ceremony=true, and no provider. It captures the exact retained predecessor and the current owner scope under the ordinary command journal; it is never a provider-selection command or browser task. The fresh explicit command may send a successor once, while restart or loss of response may only read its exact reservation. A live confirmation, accepted decision, unresolved authentication child, changed account/key/policy, or noneligible source blocks the action. A replacement presentation cannot shorten an independently live source or decision. The static desktop surface offers Sign in again, shows passive progress while the command is unresolved, then the existing provider choices appear from the owner's verified successor read. It does not launch Chrome or choose a provider on replacement. The commercial activation replacement and protected recovery presentation remain separate integration gates.

Expired prepared-source replacement is distinct from ordinary ceremony replacement. The initial and registered proof clients use the published exact-predecessor replacement contracts, their own proof purposes and the existing installation key. Before an ordinary prepare is sent, its owner retains its exact request and digest in the same transaction as its preparation claim. The owner records the verified prepared source deadline and, for registered continuation, its continuation ID without retaining a browser entry locator. These replacement coordinates have a fixed 30-day retention period from the original local source creation (within the contract's 90-day maximum); retries cannot extend it. Missing evidence, an unconfirmed prepare or an elapsed local presentation deadline does not establish a never-prepared source. The reservation store retains a single distinct successor operation ID and exact request per eligible expired predecessor and has an irreversible send claim; its caller must supply the current domain-owner authorization under the same transaction. No new source is admitted by a reservation or send claim. Accepted or committed initial results require reconciliation of original domain work; a registered commercial-reconciliation refusal cannot authorize a successor. The desktop account-connection action now reserves an eligible expired prepared source and adopts only its verified successor in the same transaction as the desktop source pointer. The successor preserves the installation, scope and original retention deadline. The replaced predecessor is fenced against stale writes. A never-sent reservation requires another explicit admitted action; a send-claimed reservation permits at most one fresh-proof exact retry of the same request under the published replacement contract. The desktop offers Continue setup without selecting a sign-in provider or opening Chrome; provider selection is a separate action after the new ordinary ceremony is ready. An accepted/committed original outcome or commercial-reconciliation refusal is retained distinctly without creating a successor. Initial successor adoption retains the Provider's optional opaque expected customer ID alongside its creator and predecessor. The successor's browser ceremony binds that identity; a later replacement cannot change or omit an already retained identity. Legacy successor records lacking the identity evidence are not reconstructed from the current browser or user.

The initial enrollment owner reconciles accepted and committed original outcomes through the original installation-handoff receipt contract. The accepted decision identifier is not the completion operation identifier; Product's original completion uses the original prepare operation identifier. A committed result naming any other completion operation is not locally recoverable. The receipt is checked against the original retained request, installation key, deadline and any original authorized scope. A receipt alone does not establish creator association or consent. Without independent retained authorized scope, the owner retains the receipt but does not construct a claim, request bootstrap grants or create an account candidate. With exact scope, the existing key-only bootstrap v3 recovery must verify the original enrollment time and return current installation/membership grants. The verified grants, original claim resolution, pending creator candidate and restored local completed enrollment projection are committed atomically within the original evidence retention bound. This projection has no browser locator or renewed hosted deadline, and the existing account-continuity owner still verifies the creator binding. Three attempts are durably bounded by 15/30/60-second retry deadlines; closed bootstrap refusal or a closed committed-receipt refusal stops automatic reads. No replay of the expired completion, fresh enrollment, sign-in selection or new consent is authorized. Packaged cross-plane qualification remains outstanding.

Protected installation-authority recovery follows the published Contracts ADR 0060 operation family. It is independent of ordinary refresh, bootstrap, account association and commercial activation. The Product source foundation uses exact registered-key proof for both prepare and deliver, verifies the pinned request and response schemas, distinguishes closed withdrawal/refusal from uncertainty, and retains one immutable recovery request in encrypted persistence. Previous-grant evidence must identify one exact original enrollment, installed key, prior installation and membership grants, and, when present, the same finalized creator approval and local grant links. An ambiguous history, still-renewable installation, missing original enrollment time, changed or revoked authority, or incomplete creator approval fails closed. The lost-enrollment variant is not admitted by this previous-grant owner; independently retained original enrollment actor evidence is required before a separate owner may use it.

The journal records preparation and delivery send claims, with two preparation attempts and three delivery attempts at bounded 15/30/60-second intervals. A prepared browser reference is available only for the exact unexpired original source. Terminal withdrawal/refusal and unresolved operations are not cleared by a different recovery ID. An explicitly expired, uncommitted original may allow a new independently admitted operation after its original deadline. Delivery cannot create or renew a recovery or extend its source deadline. The committed result must match the original enrollment time and retained actor, exact approved creator scope and grant set, signed issuer, installation, key, distinct JTIs, commitment time and current signed validity. The existing grant verifier verifies the actual JWS bytes; no response field or browser notification by itself authorizes admission. The grant references, exact local account links, retirement of superseded references, authorization epoch and nonsecret delivery receipt change in one transaction. Superseded grant/session authority is invalidated through the existing revocation primitive, not restored. No proof, authentication token or new grant JWS is stored in the recovery journal. The existing verified-grant retention rules still apply. Closed recovery refusals are retained as recovery facts, not fabricated signed refresh-denial tombstones.

This is a source foundation only: the protected v2 ceremony, v3 fresh authentication selection, exact operation command/continuation and explicit customer recovery presentation are not composed yet. Do not dispatch the new journal from ordinary onboarding, refresh, page rendering or automatic startup. Provider protected recovery remains deployment-opt-in; installed qualification must prove the nominated release, real Entra step-up and signature compatibility. No Product release or deployment approval is implied.

The coordinator delegates to existing domain services rather than duplicating their authority. Publish verified facts, separate local/Full readiness, pending operations and allowed actions. Subscribe before authoritative reads and retain invalidations received while busy. Commands carry unique operation IDs and exact expected scope/generation. Reads and renders do not initiate protected mutations. Closing a page or losing a reply cannot establish cancellation or justify another mutation.

## Confirmation

Qualify the installed native host, Windows Hello, scoped admission and provisioning restart before broad controller replacement. Cover hostile listeners, external navigation and native command denial; wrong profiles, stale presentations and entry replay; consent/permission gates, independent pairing, paused controls; duplicate actions, real worker cancellation, lost committed results and expiry; and dashboard access independent of activation. Keep offline authorization and all existing cryptographic, recovery and evidence semantics.

Architecture declarations classify the native host, coordinator and local schemas. The customer journey manifest changes with rendered states, not ahead of executable surfaces. [ADR 0056](0056-msix-packaging-and-managed-updates.md) supersedes the Inno-only packaging choice while preserving the complete frozen Brain distribution and shared WebView2. This decision grants no automatic live deployment authority.
